# イベント保存の保守メモ

2026-11-13 21:25（日本時間）の本番操作では、microCMS `/events` のPOSTが29,460ms後にHTTP 504を返した。管理画面側の通信期限による中断ではなく、保存先からの応答。Googleへの同期依頼前に停止している。読み取りは200、既存イベントは0件。管理APIのスキーマ閲覧は403のため、サービス内部のタイムアウト要因は未確認。

## 保存先

新規イベントは、店舗設定などと同じ `/menu` のJSON保存を使う。物理レコードは `kind=events`、`category=cms`、`body={bassicEventVersion:1,event:{...}}`。画像はURLと説明をJSON内に保持し、CMS画像フィールドの処理は使わない。画面上の「MENU」のメニュー品には混ぜない。

管理画面、公開サイト、カレンダー同期、過去イベント整理は `lib/event-storage.mjs` の同じ復元処理を使う。旧 `/events` は読み取り互換を残す。旧イベントの更新は新しいJSONレコードを作り、同じFacebook ID、または本文の `legacyId` で指定した旧版より優先する。旧レコードは削除しない。管理画面での削除はJSON本文の `removed=true` で記録し、旧版が再出現することを防ぐ。Google予定は自動削除しない。同じ保存方式の中で重複したイベントを勝手に統合しない。

## 失敗時

- Vercel Logsで `/api/content/events` を絞り、`CMS request failed` の `endpoint / method / kind / status / elapsedMs` を見る。本文・APIキーはログに出さない。
- 保存結果不明のときは連打せず、Facebookから読み取り直して既存登録の有無を調べる。Googleの成功は別途 `/api/calendar-status` の読み戻しで確認する。
- 読み取りだけの設定確認は External operations の `cms_readonly_diagnostics=true` で実行できる。カレンダー/SNS更新ジョブは動かない。スキーマ閲覧403は権限不足であり、権限を自動拡大しない。
- **ロールバック時もJSONイベントの読み取り互換は維持する。** 旧版のデプロイへ単純に戻すと、新形式のイベントが管理画面と同期処理から見えなくなる。表示/UIだけを戻すか、新形式リーダーを含む修正版をデプロイする。旧レコードの削除やGoogle予定の削除は復旧処理に含めない。

実イベントの登録成功を確認するまでは、タイムアウトが完全に解消したとは判定しない。本番にテスト用のイベントを作らない。

## SNS下書き

同日21:58、実イベントの保存とGoogle反映を確認済み。SNS下書き作成だけは `/menu` POSTのHTTP 400（442ms）で停止した。SNS項目も `body={bassicSocialNoticeVersion:1,notice:{...}}` にまとめ、画像・投稿先をCMSの個別フィールドに送らない。旧下書きはそのまま読める。JSONがある場合は投稿状態やスタッフ編集文を含めJSONを正とし、旧フィールドの値に戻さない。

復旧はカレンダー登録をやり直さず、「SNS下書きだけをやり直す」を使う。自動投稿の設定は変更しない。SNS下書きを作った後のロールバックでも、この形式の読み取り互換を維持する。

公開用の同期予定はGoogleの `visibility=public` を明示する。登録結果の読み戻しでも公開設定を確認し、日時・本文だけの一致を成功判定にしない。既存の手動予定は変更しない。

## 削除して操作をやり直すとき

イベントと関連下書きは管理画面で削除すると、復旧用の記録を保持して通常の一覧と同期対象から外れる。Google予定は別途、対象のID・タイトル・日時・同期元を確認して削除する。先に管理画面側を外し、定期同期による再登録を防ぐ。

同じFacebook URLを改めて登録した場合、削除済みのGoogle予定を復元できるのは、同期元の保存日時がGoogleの削除日時より新しく、同期タグとキーが一致する場合だけ。古い保存内容を使う定期実行では復元しない。所有確認や日時を確認できない場合は停止する。非公開QAカレンダーで削除後の再登録を検証する。

登録完了画面のSNSボタンは保存済み下書きを読み取るだけで、作成・再登録・投稿を実行しない。下書き編集後や画面へ戻ったときは文面を読み直す。
