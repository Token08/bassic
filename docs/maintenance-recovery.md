# Bassic 保守用：確認と復旧

店舗向けREADMEとは別の保守資料。通常の編集操作は増やさない。

## 障害の確認

- 管理画面の「詳細設定 → 公開・連携の状況」で公開サイト・ログイン保護・公開更新・イベント同期を個別に確認する。「確認できません」は成功ではない。
- GitHub Actions の **Operations watch** が毎時、読み取りだけで点検する。失敗は既存のActions通知で確認する。GitHub所有者の通知受信設定と通知先メールの受信は、本人が確認する必要がある。店舗向けのメール送信や新しい通知先は設定しない。
- 公開と同期は既存のワークフローも確認する。カレンダー同期の正常終了は個々のイベントが正しいことの保証ではない。個別の結果はイベント画面と実際の予定で確認する。
- 15分以内に公開結果を確認できなければ未確認として停止する。ページを再読み込みしても待ち時間は延長しない。保存内容を作り直さず公開サイトと実行結果を確認し、未反映なら「反映だけ」を再試行する。

## 管理画面に問題があるとき

1. Vercelの `bassic / bassic-admin` で直前の正常な本番デプロイを特定する。
2. 選んだ版の画面・認証を確認してからVercelのRollbackを実行する。未検証のURLを指定しない。
3. 本番トップ、ログイン、未ログイン時APIの401を確認する。環境変数の変更は別に追跡する。

## 公開サイトに問題があるとき

1. Actions **Publish website** と公開サイト `/_bassic-build.json` を照合する。
2. コードの問題は原因コミットを戻すPRを作り、新しい実行番号でビルド・公開する。CMSの内容が原因なら管理画面の変更履歴で対象だけを戻して確認・掲載する。
3. 最新の公開処理に失敗しただけなら、その実行の失敗箇所を確認して再実行する。DNS・メール設定は変更しない。
4. 公開ページ、画像、PDF、管理画面の認証を読み取り確認する。

公開前に、現在配信済みの署名付きパッケージをGitHub Release `bassic-production` の `bassic-site.previous.release` に1世代保持する。対応する `bassic-site.previous.json` にrun・commit・SHA256を記録する。未配信の候補でバックアップを上書きせず、現在の配信版を確保できなければ公開を止める。これはコード・静的出力の復旧材料であり、CMSやGoogleのデータのバックアップではない。

**古い署名付きパッケージをそのまま本番へ再アップロードしない。** サーバーは古い実行番号を拒否する。復旧も新しいビルド・署名・実行番号で行う。

## カレンダーに問題があるとき

- コードのロールバックではGoogleの予定やSNS投稿は元に戻らない。対象日・予定ID・部分成功の結果を確認し、まとめて削除しない。
- 緊急停止が必要なら、店休日の直接変更はVercelの `GOOGLE_CALENDAR_CLOSED_DAYS_ENABLED=false` と再デプロイ、イベントの定期同期はGitHub変数 `ENABLE_CALENDAR_SYNC=false` で止める。停止理由と再開時刻を記録し、再開前に保存先を確認する。
- 読み込みエラー時は変更を禁止する。部分失敗は成功分を再追加せず未完了分だけ確認して再試行する。

## 本番を汚さずに確認する

`node --test scripts/operations-health.test.mjs`、`python3 scripts/backup-public-release.test.py` と隔離環境のブラウザテストを使う。本番には確認用のイベント・店休日・文章を登録しない。実際の店舗担当者による一連の操作確認は、次の実更新時に行う。それまではスタッフ確認済みとしない。
